# Xtensa Toolchain Checkpoint

This checkpoint records how far the open firmware path has moved from analysis into buildable code.

## Plain Result

We now have a local Xtensa assembler, linker, objcopy, readelf, and objdump that can produce big-endian Xtensa ELF files matching the broad shape of the HP firmware payload.

That is enough for a first non-printing firmware experiment in assembly: boot, do almost nothing, and later grow toward safe USB identity/status handling. It is not yet a full C firmware toolchain.

No printer was touched during this checkpoint.

## Proven Locally

- crosstool-NG produced working `xtensa-fsf-elf` binutils under `/tmp/hp1020-ctng-mnt/x-tools/xtensa-fsf-elf/bin/`.
- The assembler accepts real Xtensa instructions.
- The linker emits `ELF 32-bit MSB executable, Tensilica Xtensa`.
- The disassembler decodes the generated bytes correctly.
- `scripts/probe-xtensa-binutils.sh` repeats the smoke test and writes results to `analysis/toolchain-probe/binutils-smoke/`.

The generated smoke-test program is intentionally harmless and tiny:

```asm
_start:
    entry a1, 16
    movi a2, 0
    retw
```

## Why This Matters

The project does not need a complete C firmware compiler before making progress. The first safe prototype can be an assembly-only payload because the early target is narrow:

- boot into known code
- avoid print engine/video/fuser/motor registers
- touch only the safer USB-facing surface after more mapping
- prove whether the printer accepts and runs a replacement payload at all

That first payload would not print. It would only answer the question: can our own code run without relying on the HP blob?

## Next Engineering Step

Build a minimal firmware layout from our own assembly:

- reproduce the HP wrapper shape: 8-byte date prefix plus Xtensa ELF payload
- choose conservative load addresses from the existing HP ELF map
- include a real reset/entry path
- keep the payload in an infinite idle loop at first
- inspect the final file with the same readelf/objdump checks

Printer-side testing should wait until that payload passes the static safety gate and contains no engine/video MMIO access.
